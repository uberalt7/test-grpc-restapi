# Speed Camera Snapshot Service

Микросервис для демонстрации работы с gRPC и REST API поверх общего слоя бизнес-логики. Сервис принимает данные о фиксации скорости камерой, сохраняет их в SQLite и предоставляет методы для создания и фильтрации записей.

## Структура проекта

```
├── cmd/
│   ├── app/          # Точка входа: запуск REST и gRPC серверов
│   ├── client/       # Тестовый клиент с бенчмарком REST vs gRPC
│   └── seed/         # Скрипт для генерации и заполнения тестовой БД
├── internal/
│   ├── domain/       # Бизнес-модели и интерфейсы
│   ├── gen/
│   │   └── camera/   # Сгенерированный код из .proto (не коммитится в Git)
│   ├── repository/   # Реализация работы с SQLite
│   ├── service/      # Бизнес-логика (Use Cases)
│   └── transport/
│       ├── grpc/     # gRPC сервер
│       └── http/     # REST API сервер
├── proto/            # Protobuf контракты
├── go.mod
└── README.md
```

## Требования

1. **Go** (версия 1.21 или выше).
2. **Protoc compiler** (`protoc`) и плагины для Go:
   - Установите `protoc` и добавьте его в `PATH`.
   - Установите плагины:
     ```bash
     go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
     go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest
     ```
3. **CGO**: Для работы драйвера `github.com/mattn/go-sqlite3` требуется включенный CGO.
   - **Linux/macOS**: Обычно включен по умолчанию.
   - **Windows**: Убедитесь, что установлен GCC (например, через MSYS2 или TDM-GCC), и переменная окружения `CGO_ENABLED=1`.

## Установка и запуск

### 1. Установка зависимостей

```bash
go mod tidy
```

### 2. Генерация gRPC-кода

Выполните из корня проекта (где лежит `go.mod`):

```bash
protoc --go_out=. --go-grpc_out=. proto/camera.proto
```

Файлы будут сгенерированы в `internal/gen/camera/`.

### 3. Генерация и заполнение БД

Файл базы данных `camera.db` не хранится в Git. Перед запуском сервера его нужно создать и заполнить тестовыми данными (150 записей за последние 30 дней):

```bash
go run cmd/seed/main.go
```

После выполнения в корне проекта появится файл `camera.db`.

### 4. Запуск сервера

```bash
go run cmd/app/main.go
```

Сервер запустит два интерфейса одновременно:
- **REST API**: `http://localhost:8080`
- **gRPC API**: `localhost:50051`

## Тестирование API

### REST API

#### Linux / macOS (Bash / Zsh)

Используйте стандартный `curl`. Обратите внимание на одинарные кавычки для JSON, чтобы избежать проблем с экранированием.

**Создать снимок:**

```bash
curl -X POST http://localhost:8080/api/v1/snapshots \
  -H "Content-Type: application/json" \
  -d '{"license_plate": "A777AA77", "color": "black", "speed": 180}'
```

**Получить все записи (без ID):**

```bash
curl http://localhost:8080/api/v1/snapshots
```

**Получить записи с фильтрами (черные машины, скорость от 100 до 200):**

```bash
curl "http://localhost:8080/api/v1/snapshots?color=black&speed_from=100&speed_to=200"
```

#### Windows (PowerShell)

В PowerShell стандартный `curl` имеет проблемы с экранированием кавычек и кириллицей. Рекомендуется использовать нативный командлет `Invoke-RestMethod`, который сам корректно формирует JSON.

**Создать снимок:**

```powershell
Invoke-RestMethod -Uri "http://localhost:8080/api/v1/snapshots" -Method Post -Body (@{license_plate="A777AA77"; color="black"; speed=180} | ConvertTo-Json) -ContentType "application/json"
```

**Получить записи с фильтрами:**

```powershell
Invoke-RestMethod -Uri "http://localhost:8080/api/v1/snapshots?color=black&speed_from=100"
```

Если вы всё же хотите использовать `curl.exe` в PowerShell, используйте удвоение кавычек:

```powershell
curl.exe -X POST http://localhost:8080/api/v1/snapshots -H "Content-Type: application/json" -d "{""license_plate"":""A777AA77"",""color"":""black"",""speed"":180}"
```

### gRPC API

Для тестирования gRPC используйте встроенный клиент:

```bash
go run cmd/client/main.go
```

Клиент подключится к серверу на порту `50051`, выполнит тестовые запросы и выведет результаты в консоль.

Альтернативно, вы можете использовать Postman (версия 10+), Insomnia или BloomRPC. Для этого импортируйте файл `proto/camera.proto` и укажите адрес `localhost:50051`.

## Бенчмарк REST vs gRPC

Проект включает встроенный бенчмарк, который сравнивает производительность REST и gRPC с учётом времени работы базы данных.

### Запуск бенчмарка

Убедитесь, что сервер запущен, и выполните:

```bash
go run cmd/client/main.go
```

### Что измеряет бенчмарк

Бенчмарк выполняет следующие операции 1000 раз для каждого метода:

1. **Direct DB** — прямое обращение к SQLite (эталонное время работы с БД).
2. **REST API** — полный цикл: HTTP-запрос + сериализация/десериализация JSON.
3. **gRPC API** — полный цикл: gRPC-запрос + сериализация/десериализация Protobuf.

Для каждой операции вычисляется **Overhead** — накладные расходы на сериализацию, передачу данных и десериализацию (общее время минус время работы с БД).

### Подготовка данных

Перед тестами бенчмарк автоматически:
- Добавляет 100 записей с уникальным цветом для теста `List` (чтобы количество возвращаемых данных было константным).
- Использует уникальный цвет для теста `Create` (чтобы не накапливать данные).
- Удаляет все тестовые записи после завершения.

### Пример вывода

```

Тестовые данные: номер BENCH001, скорость 160

Подготовка тестовых данных для List...
Добавлено 100 записей с цветом 'bench_list_unique_color' для теста List.

Direct DB (SQLite)
Create (среднее за 1000 итераций): 1.15ms
List (среднее за 1000 итераций): 5.25ms

REST API (HTTP)
Create (среднее за 1000 итераций): 1.35ms
List (среднее за 1000 итераций): 5.85ms

gRPC API
Create (среднее за 1000 итераций): 1.40ms

```

### Интерпретация результатов

Для простых операций с маленькими данными на localhost в Go разница между REST и gRPC составляет 50-100 микросекунд. Это нормальный результат, так как:

- SQLite работает in-process (нет сетевых задержек между приложением и БД).
- Стандартная библиотека Go для JSON сильно оптимизирована.
- HTTP/1.1 Keep-Alive в Go работает очень эффективно.

gRPC показывает преимущество при сложных вложенных структурах, больших объёмах данных, сетевом взаимодействии между разными машинами и множественных последовательных вызовах.

## Возможные проблемы и решения

### Ошибка `package ... is not in std` при запуске

Убедитесь, что вы выполнили команду `protoc` из корня проекта, и что в файле `proto/camera.proto` указана строка:

```protobuf
option go_package = "speedcamera/internal/gen/camera";
```

Замените `speedcamera` на имя вашего модуля из `go.mod`, если оно отличается.

### Ошибка компиляции `sqlite3` (особенно в Windows)

Убедитесь, что переменная окружения `CGO_ENABLED` установлена в `1`. В PowerShell:

```powershell
$env:CGO_ENABLED="1"
```

Также проверьте наличие установленного GCC-компилятора в системе.

### Ошибка `Invalid JSON` при curl в Windows

Используйте `Invoke-RestMethod` (как показано выше) или замените кириллические символы в номере машины на латинские, чтобы избежать проблем с кодировкой консоли Windows (UTF-8 vs CP1251).

### Ошибка `protoc: command not found`

Убедитесь, что вы установили `protoc` и добавили путь к нему в переменную окружения `PATH`. Также проверьте, что пути к `protoc-gen-go` и `protoc-gen-go-grpc` (обычно `C:\Users\<ВашеИмя>\go\bin`) добавлены в `PATH`.

## Архитектура

Проект демонстрирует разделение ответственности (Clean Architecture):

- **Domain** — бизнес-модели и интерфейсы, не зависят от внешних библиотек.
- **Repository** — реализация работы с SQLite, зависит только от Domain.
- **Service** — бизнес-логика, зависит только от Domain.
- **Transport** — HTTP и gRPC серверы, зависят от Service.

Одна и та же бизнес-логика (`internal/service`) обслуживает оба транспортных протокола без дублирования кода. Это позволяет легко добавлять новые протоколы (например, GraphQL) без изменения бизнес-логики.
